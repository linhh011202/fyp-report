\subsection{Payment \& Subscription Management}%
\label{sec:payment}

This subsection documents how the payment processing and subscription management system integrates Stripe, a leading payment processor, with a local database to track user subscriptions and enforce plan limits. The implementation is organised into three core modules that work together to handle the complete lifecycle of user subscriptions.

\subsubsection{Payment System Overview}

Figure~\ref{fig:payment_architecture_simple} illustrates the payment system architecture, showing how the three backend modules interact with Stripe and the data stores.

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth]{images/payment_architecture_simple.png}
\caption{Payment System Architecture}
\label{fig:payment_architecture_simple}
\end{figure}

The system consists of three modules that work in concert. The \textbf{Payment Processing} module acts as the bridge to Stripe's infrastructure, handling checkout sessions, listening for payment events via webhooks, and retrieving pricing information. The \textbf{Subscription Tracking} module maintains a local record of each user's subscription status, including their current plan, validity dates, and usage consumption against their quota. The \textbf{Plan Management} module stores the definitions of subscription tiers (Free, Basic, Pro) with their associated features and quota limits, using Redis caching for performance. Together, these modules ensure that payment information from Stripe is reflected in the application's database, and that users' access to features is governed by their active subscription state.

\subsubsection{Checkout and Payment Flow}

Figure~\ref{fig:checkout_flow_simple} illustrates the step-by-step checkout process when a user subscribes to a plan.

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth]{images/checkout_flow_simple.png}
\caption{Stripe Checkout Flow}
\label{fig:checkout_flow_simple}
\end{figure}

The flow begins when the user selects a subscription plan on the dashboard. The frontend requests a checkout session from the backend, which creates a secure payment session with Stripe. The user is then redirected to Stripe's hosted payment page, where they enter their payment details in a secure environment managed entirely by Stripe. Upon successful payment, Stripe sends a confirmation notification (webhook) back to the backend, which activates the subscription in the local database. Finally, the user sees a confirmation message on the dashboard. This design keeps payment processing secure by delegating it entirely to Stripe while maintaining a synchronised local copy of subscription data for feature enforcement.

\subsubsection{Subscription Lifecycle}

A subscription passes through several states throughout its lifetime. Figure~\ref{fig:subscription_lifecycle_simple} shows these states and the transitions between them.

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth]{images/subscription_lifecycle_simple.png}
\caption{Subscription Lifecycle State Diagram}
\label{fig:subscription_lifecycle_simple}
\end{figure}

The lifecycle works as follows:

\begin{enumerate}
    \item \textbf{New Subscription}: When payment completes, the system records the subscription as active, sets the access period (start and end dates), and initialises the user's usage quota based on the selected plan.

    \item \textbf{Renewal}: At the end of each billing period, Stripe automatically charges the customer. The application detects this renewal event and extends the access period forward (e.g., by 30 days for monthly plans) while resetting usage counters to zero, giving the user a fresh allocation for the new period.

    \item \textbf{Cancellation}: When a user requests cancellation, the subscription is marked as pending cancellation. The user retains full access until the current billing period naturally expires, providing a graceful experience.

    \item \textbf{Expiration}: Once the billing period ends, the status changes to expired and the user loses access to premium features.

    \item \textbf{Plan Change}: Users can schedule an upgrade or downgrade. Rather than applying changes immediately, the system schedules the new plan to take effect at the start of the next billing cycle, avoiding billing complications.
\end{enumerate}

\subsubsection{Plan Management and Versioning}

Figure~\ref{fig:plan_versioning_simple} illustrates how plan versions are managed when administrators update subscription tiers.

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth]{images/plan_versioning_simple.png}
\caption{Plan Versioning and Subscriber Impact}
\label{fig:plan_versioning_simple}

When administrators need to modify plans---such as adjusting quota limits or updating feature descriptions---the system creates a new plan version rather than overwriting the old one. This approach preserves a historical record and ensures that existing subscribers continue to benefit from the terms of their originally purchased plan while new subscribers receive the updated terms. Plan data is heavily cached in Redis (refreshed automatically when new versions are created) to minimise database queries, since plan information is requested on every page load.

\subsubsection{Webhook Synchronisation}

Webhooks are critical for keeping the local subscription database synchronised with Stripe's authoritative payment records. Figure~\ref{fig:webhook_flow_simple} shows how the system processes different types of Stripe events.

\begin{figure}[H]
\centering
\includegraphics[width=0.75\textwidth]{images/webhook_flow_simple.png}
\caption{Stripe Webhook Processing Flow}
\label{fig:webhook_flow_simple}
\end{figure}

Whenever a significant payment event occurs in Stripe, it sends a webhook notification to the application. The backend first verifies the message authenticity to ensure it genuinely comes from Stripe, then routes it based on event type. A \textbf{Payment Completed} event triggers subscription activation in the local database. A \textbf{Subscription Renewed} event resets usage quotas for the new billing period. A \textbf{Plan Change Applied} event updates the subscription to reflect the new plan and its associated quotas. Unrecognised events are logged and safely ignored. By using webhooks rather than polling Stripe repeatedly, the system achieves real-time synchronisation with minimal overhead.

\subsubsection{Quota and Usage Tracking}

The system enforces plan limits by tracking usage against quota. Each subscription record stores the total resource allowance per billing period (quota) and the amount already consumed (usage). Before allowing a resource-intensive operation such as transcribing audio, the system checks whether current usage exceeds the quota. This check occurs independently for each type of quota (e.g., batch processing minutes and live transcription minutes), allowing fine-grained control. When a subscription renews, usage counters reset to zero while quota limits remain fixed, giving users a fresh allocation each period.

\subsubsection{Caching Strategy}

To reduce latency and database load, the system caches frequently accessed data in Redis. Plan definitions are cached for one hour (since they change infrequently but are queried on every page load), and Stripe price information is cached for 24 hours to avoid repeated external API calls. Both caches use a protective technique: if a requested item does not exist, the system temporarily remembers that it is missing (for 60 seconds), preventing repeated lookups for non-existent items that could otherwise overwhelm the system under heavy load. The caching layer is transparent to the rest of the application and is automatically invalidated when administrators update plan information.
